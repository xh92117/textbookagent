编排架构全景
智能体编排层是 LLM 与工具/记忆/知识之间的"总线"，负责工具调度、消息流转、上下文管理和错误恢复。
🔗
AgentProtocol 编排协议
AgentProtocol 是智能体与 LLM 之间的调度核心，管理完整的工具调用循环。

🔄 工具调用循环

  • LLM 返回 tool_use 块 → AgentProtocol 解析工具名和参数
  • ToolManager 查找注册工具 → 执行 → 返回 ToolResult
  • 结果注入为 tool_result 消息 → 再次调用 LLM
  • 循环直到 LLM 返回 final_answer 或达到最大轮次
  • 每轮自动记录到 RealtimeMemoryRecorder

🛡️ 安全与容错

🔒

工具白名单

技能通过 allowed-tools 限制可用工具，防止越权调用

🔄

错误恢复

工具执行失败返回 ToolResult.fail，LLM 收到错误信息后可重试或换策略

⏹

取消信号

cancel_event 贯穿整个调用链，工具执行中可被中断

📊

Token 预算

每轮检查 Token 预算，超限触发渐进压缩或裁剪

工具注册与调度
所有工具继承 BaseTool，通过 ToolManager 统一注册和调度。工具分为 PRE_PROCESS（主动调用）和 POST_PROCESS（自动执行）两个阶段。

网页搜索与知识库耦合
multi-search-engine 技能定义了搜索→抓取→保存的完整工作流，通过 allowed-tools 将 web_fetch 和 knowledge_capture 绑定在一起。

🔍 搜索引擎降级策略

1️⃣

Brave 优先

优先使用 Brave 搜索，单次探测查询，不并行多查

2️⃣

Bing 回退

Brave 返回 429/验证码时标记不可用，切换 Bing 英文搜索

3️⃣

直接源兜底

两个引擎都失败时，直接抓取已知高质量 URL（官方文档/标准/论文）

🚫

避免重试

不重复使用已失败的引擎，不尝试 Google/Baidu（返回验证页）

⚡ 即时保存原则

SKILL.md 明确要求：每抓取一个可信原始来源，立即调用 knowledge_capture 保存，而非等到搜索结束后批量保存。

原因：长搜索会话可能被上下文压缩，未保存的来源会丢失。即时保存确保每个有价值的来源都被持久化到知识库。

保存数量指引：

  • 章节编写：3-6 个持久来源
  • 广泛研究：6-12 个持久来源
  • 足够后停止搜索，避免过度消耗
📥
knowledge_capture 捕获机制
knowledge_capture 是网页搜索与知识库之间的"桥梁工具"，将 LLM 判断有价值的网页内容持久化为 Markdown 知识来源。

🔄 捕获→索引→检索 闭环

1

web_fetch 抓取原始来源

智能体使用 web_fetch 打开搜索结果中的原始 URL，获取网页全文或下载文档。web_fetch 自动检测编码、提取正文、截断超长内容。

2

knowledge_capture 立即保存

LLM 判断内容有价值后，立即调用 knowledge_capture。工具执行 5 重质量检查，通过后调用 KnowledgeService.save_web_source() 写入 Markdown 文件到 knowledge/{book_id}/sources/。

3

KnowledgeService 持久化

保存为带 YAML Front Matter 的 Markdown 文件，包含 url、title、reason、tags、saved_at 等元数据。同时更新知识库索引。

4

mark_dirty() 触发同步

knowledge_capture 保存成功后，调用 MemoryManager.mark_dirty() 标记索引脏位。下次 memory_search 或 sync() 时，新增的知识来源文件会被分块、生成 Embedding、写入 SQLite + FTS5 索引。

5

memory_search 检索召回

后续章节编写时，WriterAgent 通过 memory_search 检索知识库，向量+关键词双路融合返回相关证据。之前捕获的网页内容作为 Evidence Pack 注入写作上下文。

🗄️
记忆存储引擎
记忆系统使用双引擎存储：SQLite + FTS5（结构化索引+全文搜索）和文件系统（Markdown 原文），通过 MemoryManager 统一调度。

🗄️ SQLite 存储层

# MemoryStorage 核心表结构 CREATE TABLE chunks ( id INTEGER PRIMARY KEY, file_path TEXT, start_line INTEGER, end_line INTEGER, content TEXT, file_hash TEXT, updated_at TEXT ); # FTS5 全文索引 CREATE VIRTUAL TABLE chunks_fts USING fts5(content, tokenize="unicode61"); # 向量存储 CREATE TABLE embeddings ( chunk_id INTEGER, vector BLOB, # 序列化 float32 model TEXT, dim INTEGER ); # 文件追踪 CREATE TABLE files ( path TEXT PRIMARY KEY, hash TEXT, updated_at TEXT );

🔄 同步流程 (sync)

📂

1. 扫描文件

遍历 MEMORY.md、memory/、knowledge/、textbooks/ 下所有 MD 文件

🔍

2. 哈希比对

SHA-256 比对文件内容，跳过未修改文件，仅处理变更

✂️

3. 文本分块

Chunker 按 500 token/块、50 token 重叠分块

📊

4. 向量+索引

生成 Embedding 向量，写入 SQLite + FTS5 索引

🗑️

5. 清理旧数据

删除已变更文件的旧 chunks 和 embeddings，保持索引一致

🔄
端到端耦合链路
从用户请求到知识沉淀再到检索召回，完整的闭环数据流。

🔗 三大耦合点

🌐→💾

搜索→捕获耦合

multi-search-engine 技能通过 allowed-tools=[web_fetch, knowledge_capture] 强制绑定。SKILL.md 规定"每抓取一个来源立即保存"。

💾→🗂️

捕获→索引耦合

knowledge_capture 保存成功后调用 memory_manager.mark_dirty()，触发增量同步将新文件索引入 SQLite + FTS5。

🗂️→🔍

索引→检索耦合

memory_search 同时检索记忆文件和知识库文件，向量+关键词双路融合，确保捕获的知识可被召回。
